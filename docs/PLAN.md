## 📌 결정 로그

향후 작업자(사람/에이전트)가 결정을 뒤집지 않도록 결정과 근거를 남긴다.

### D-001. TanStack Query를 도입하지 않는다 (2026-08-11)

**결정**: 서버 상태 캐싱을 위해 TanStack Query를 도입하지 않는다.

**근거**:

- 클라이언트 데이터 흐름은 댓글 하나뿐이고, Server Action + `revalidatePath`로 이미 동작한다.
- 폴링, 무한스크롤, 윈도우 포커스 refetch, 컴포넌트 간 캐시 공유가 없다. 라이브러리의 핵심 가치를 활용할 부분이 없다.
- 댓글의 체감 지연은 React 19 `useOptimistic`으로 해결할 수 있다. 의존성 없이 같은 결과를 얻는 방식을 우선한다.

**재검토 조건**: 검색 기능(`T-402`)을 도입할 경우. 검색어별 캐시, `placeholderData: keepPreviousData`, 자동 요청 취소는 RSC나 `useOptimistic`으로 대체하기 번거롭다. 재도입은 `pnpm add` + provider 마운트로 끝난다.

### D-002. 문서 구조 원칙 (2026-08-11)

**결정**:

- 규칙은 `AGENTS.md` 단일 파일로 유지한다. 분리는 400줄을 넘거나 특정 디렉토리 전용 규칙이 쌓일 때만 하며, 그때도 글롭 룰 파일이 아닌 중첩 `CLAUDE.md`(해당 디렉토리에서 작업할 때만 로드) 방식을 쓴다.
- 구현 상세 스펙과 이 백로그는 `docs/`에 둔다. 규칙과 겹치는 내용은 `AGENTS.md` 포인터로 대체한다.
- **DB 스키마의 원본은 `supabase/schema.sql`다.** 마이그레이션 러너가 없으므로 idempotent 단일 파일로 유지한다. `database.md`는 읽기용 요약이다.
- 파일 단위 디렉토리 트리를 문서에 두지 않는다. 구조의 원본은 코드다.

**근거**: 코드와 같은 커밋에서 갱신할 수 있고, 문서를 줄이고 모을수록 코드와 어긋날 가능성이 작아진다.

### D-003. 홈은 EyePoster + 뉴스 + 최신 글만, 본문 prose는 단일 출처 (2026-08-20)

**결정**:

- 홈 포스터는 `EyePoster`(방범카메라) 하나다. 시그니처는 하나여야 한다.
- 홈은 시각적인 제목이나 인사말 없이 포스터(1/5) + 최신 뉴스(4/5)로 바로 시작한다. 문서 아웃라인용 `sr-only` h1("neruu00.log")만 둔다.
- 본문 prose 스타일은 `globals.css`의 `.prose` 오버라이드를 단일 출처로 삼는다. 페이지별 인라인 `prose-*` 체인은 금지한다. `prose`는 `PostContent`·`TiptapEditor`·뉴스 상세 래퍼 세 곳에만 붙는다.

**주의**: 인사말이나 기술 스택 루프처럼 두 번째 포스터를 넣자는 제안이 나오면 이 로그를 근거로 소유자에게 먼저 확인한다.

### D-004. 좋아요 기능을 두지 않는다 (2026-08-20)

**결정**: 좋아요 기능을 두지 않는다. 로그인은 댓글을 쓰기 위해서만 사용한다.

**근거**:

- 가장 복잡한 클라이언트 상태 머신, 테이블·인덱스·RPC·비정규화 컬럼, 상세 화면마다 추가 쿼리를 감수하고 얻는 것은 로그인 사용자만 누를 수 있는 하트 하나였다.
- 대다수 방문자(비로그인)에게는 "로그인이 필요합니다"라는 거절 경험만 줬다.
- 참여 신호는 view_count + GA4로 충분하다.

**재검토 조건**: 방문자 반응 수단이 필요해지면 로그인 없는 익명 반응(쿠키 기반 등)을 새로 설계한다. 라이브 DB DROP은 T-312.

### D-005. 게시글 본문은 서버에서 정적 렌더링한다 — `@tiptap/static-renderer` (2026-08-27)

**결정**: 읽기 화면의 본문을 클라이언트 Tiptap 에디터 대신 `@tiptap/static-renderer`를 사용해 서버 컴포넌트(`PostContent`)에서 렌더링한다.

**근거**:

- 클라이언트 에디터(`immediatelyRender: false`)는 서버에서 null을 반환하므로 본문이 SSR 응답에 없다. 검색엔진·링크 미리보기가 본문을 보지 못한다.
- 읽기 전용 페이지에 편집 런타임 전체가 포함된다.
- 서버에서 헤딩 id를 붙여야 `#heading` 딥링크가 첫 로드부터 동작한다.

**왜 이 패키지인가**: `@tiptap/core`의 `generateHTML`은 DOM이 필요해 서버에서 쓸 수 없고, `@tiptap/html`은 `zeed-dom` 셰도우 DOM에 의존한다. `@tiptap/static-renderer`는 Tiptap 3 공식 패키지로, DOM 없이 JSON → React 요소를 만들고 노드별 매핑 오버라이드로 코드블록·이미지·테이블·Mermaid를 우리 컴포넌트로 바꿔 끼울 수 있다. 버전은 나머지 Tiptap 패키지와 맞춰 고정한다.

**따라오는 제약**: 스키마/노드뷰 분리, 에디터와 `POST_SCHEMA` 동기화 — `editor.md`, `AGENTS.md` "반드시 알아야 할 것" 4번.

**재검토 조건**: 본문에 클라이언트 상호작용(접기, 탭, 실행 가능한 코드 등)이 필요해질 때. 그때도 뷰어 전체를 클라이언트로 돌리지 않고 해당 노드 매핑만 클라이언트 컴포넌트로 바꾼다 — Mermaid가 그 선례다.

### D-006. mermaid는 동적 import + 뷰포트 진입 시 렌더 (2026-09-16)

**결정**: `MermaidDiagram`에서 mermaid를 정적 import하지 않고 그릴 때 `import('mermaid')`로 불러온다. 다이어그램은 뷰포트에 가까워졌을 때만 렌더링한다(`useInViewOnce`, `rootMargin: '200px 0px'`). `mermaid.initialize()`도 동적 로더 안에서 한 번만 실행한다.

**근거**: 게시글 LCP를 늦춘 원인은 mermaid 렌더링 대기가 아니라 메인 스레드 블로킹이었다. 본문은 서버에서 렌더링하므로 먼저 나오고, LCP 요소도 본문 텍스트다.

- 정적 import하면 mermaid + d3 + dompurify가 `/posts/[id]` 라우트 번들에 들어가 **다이어그램이 없는 글에서도** 이를 내려받아 실행한다.
- 첫 화면 밖의 다이어그램까지 로드 시점에 모두 그리면 메인 스레드를 점유한다.
- 적용 후 로컬 측정(4x CPU): `/posts/[id]` First Load JS 308 → 157 kB, LCP 2176 → 1024 ms.

**측정 주의**: 회차별 편차가 크다. slow 4G 조건에서는 3회만 측정하면 이상치 하나로 중간값이 뒤집히므로 7회 이상 측정해야 방향이 안정된다.

**남은 것**: 상세 페이지는 요청마다 SSR로 렌더링되고 `isAdmin()` → `getPost()` → 인접 글 조회가 직렬로 실행된다. 실제 부하에서 TTFB를 다시 확인한다.

**재검토 조건**: 다이어그램이 첫 화면 안에 있는 글이 많아지면 `rootMargin`을 키우거나 첫 다이어그램만 즉시 렌더링하는 예외를 둔다. 정적 import로 되돌리지는 않는다 — 다이어그램이 없는 글까지 비용을 치르게 된다.

### D-007. 게시글 시리즈는 별도 테이블과 명시적 순서를 사용하고, 전용 페이지는 만들지 않는다 (2026-09-29)

**결정**: `series` 테이블을 두고 `posts.series_id`·`series_order`로 연결한다. 시리즈 목록·상세 페이지는 만들지 않는다. 글 작성 화면에서 시리즈를 지정하고, 게시글 상세 화면에서만 시리즈 목록을 보여 준다. 시리즈 글의 이전/다음 글은 시리즈 내 앞뒤 편이다.

**근거**:

- 태그(`series:xxx`)나 `posts.series` 텍스트 컬럼을 사용하면 오타 하나로 시리즈가 나뉘고, 이름을 바꿀 때 소속 글을 모두 수정해야 한다.
- `created_at` 순서만 사용하면 이미 작성한 글 사이에 새 편을 끼워 넣을 수 없다. `series_order`는 비워 두면 서버가 채우므로 입력 부담도 없다.
- 1인 블로그라 시리즈 수가 적어 전용 페이지를 만들어도 얻는 이점이 크지 않다.

**편집 방식**: 제목 입력란 앞의 시리즈 버튼으로 다이얼로그를 연다. 이 글의 시리즈 선택·새 시리즈·위치는 글을 저장할 때 반영하고, 시리즈 이름 변경·삭제는 즉시 반영한다. 기준은 "이 글의 배치인가, 시리즈 자체인가"다. 이 글의 위치를 옮기면 다른 글의 번호도 밀리지만, 이 글을 저장하면서 발생한 변경이므로 저장 시점에 함께 반영한다. 다이얼로그에서는 이 글만 움직일 수 있고 다른 글의 순서는 바꾸지 않는다.

**순서 저장**: `posts.series_order`를 유지하고, 위치를 지정하면 목록에 끼워 넣은 뒤 순서가 바뀐 글만 나눠서 UPDATE한다. `series.post_order` 배열도 검토했지만 FK 조인을 쓸 수 없고 배열 정렬·보정 코드가 늘어 비용이 더 컸다. UPDATE가 중간에 실패하면 순서가 겹칠 수 있지만 `created_at` 순으로 이어서 정렬하며, 다음 저장 때 정리된다. 이 문제가 실제로 발생하면 같은 로직을 RPC로 옮긴다.

**재검토 조건**: 시리즈가 늘어 한눈에 모아 볼 공간이 필요해지면 `/series` 목록을 추가한다. 이때 `series`에 `slug`·`description`을 추가한다.

### D-008. 포트폴리오에만 Windows 95 테마를 적용한다 (2026-10-01)

**결정**: `/projects`를 `/portfolio`로 옮기고 별도 라우트 그룹 `(portfolio)`로 분리한다. 이 그룹에서는 SideNav 대신 Windows 95 바탕화면·작업 표시줄을 쓰고, 진입 시 부팅 화면을 보여준다. 바탕화면에는 `about` 앱과 `project` 폴더만 둔다. 실제 경로는 `/portfolio` 하나만 두고, 창은 가상 경로로 열어 여러 개를 동시에 띄운다. 바탕화면과 제목줄에는 브랜드 주황색을 적용한다. 기존 `/about`, `/projects` 주소는 `/portfolio?open=…`으로 영구 리다이렉트한다.

주소별로 창을 하나씩 여는 방식은 한 번에 창을 하나만 띄울 수 있어 바탕화면처럼 쓰기 어려웠다. 방식을 바꾸면 프로젝트 문서별 URL과 사이트맵 항목이 사라진다. 외부 링크에서는 `open` 파라미터로 해당 창을 바로 열 수 있도록 보완한다.

**근거**: 블로그 전체에 레트로 스타일을 적용하면 긴 글의 가독성과 모바일 사용성이 떨어진다. 포트폴리오는 첫 방문자에게 인상을 남기는 화면이라 테마 적용 효과가 크고, 정적 데이터를 사용하므로 작업 범위도 작다. 프로젝트 문서 본문도 픽셀 폰트로 통일해 화면 전체가 하나의 데스크톱처럼 보이게 한다. 12px 픽셀 폰트로 긴 글을 읽기는 불편할 수 있어 줄 간격을 넉넉히 두고, 문단을 그룹 상자로 나눠 작은 단위로 묶는다.

**재검토 조건**: 테마를 블로그의 다른 화면으로 확대하려면 플랫 & 미니멀 규칙 자체를 다시 정해야 한다. 화면마다 예외를 추가하지 않는다.

## ⏳ 라이브 반영·확인 대기

코드/SQL은 있지만 라이브 시스템에 반영하지 않았거나 확인하지 못한 항목.

- [ ] **T-308** `supabase/schema.sql`의 **`tech_news` 중복 정리 + `original_url` UNIQUE 인덱스 블록이 라이브 DB에 적용되지 않았다.** 파일 안에 ⚠️ 주석으로 표시돼 있다. Supabase SQL Editor에서 실행한 뒤 해당 주석을 지운다. 애플리케이션의 중복 체크는 `published_at >= sinceDate` 범위 안에서만 동작하므로 이 제약이 최종 방어선이다.
- [ ] **T-312** 좋아요 테이블·RPC·`posts.like_count`의 **라이브 DB DROP을 실행하지 않았다.** `schema.sql`의 ⚠️ 블록을 Supabase SQL Editor에서 실행한 뒤 블록을 삭제한다. 코드는 like 객체를 참조하지 않으므로 실행 전에도 앱은 정상 동작한다. 실행은 사람이 한다.
- [ ] **T-003** 뉴스 크론 정상 동작 확인 — 실제 크론 응답에서 `feedsFailed: 0`, `failed: 0`을 확인한 기록이 없다. 확인 후 이 항목을 지운다.

## 🔒 T-1. 보안 · 데이터 무결성

- [ ] **T-101** **조회수 조작 차단** — `incrementViewCount`(`actions/post.ts`)는 인증이 없는 public server action이고 중복 방지는 클라이언트 쿠키(`components/post/ViewCounter.tsx`)에서만 처리한다. 액션을 직접 호출하면 무한히 증가한다. IP+postId 기반 서버 측 기록 또는 rate limit이 필요하다.
- [ ] **T-102** **RLS 분리** — `lib/supabase.ts`가 공개 조회부터 관리자 쓰기까지 `service_role` 단일 클라이언트로 처리해 RLS를 전면 bypass한다. 서버 액션 하나에서 권한 체크가 누락되면 곧바로 DB 전체가 노출된다. 공개 읽기를 anon 키 + RLS로 분리하고, 나아가 NextAuth 세션을 기반으로 Supabase JWT를 발급해 익명 읽기·관리자 쓰기를 **DB 엔진 레벨에서** 통제한다.
- [ ] **T-103** **댓글 rate limit** — 로그인만 하면 댓글을 무제한으로 작성할 수 있다.
- [ ] **T-105** Vercel의 미사용 시크릿 `OTP_SECRET`, `SESSION_SECRET` 정리 — 코드에서 참조 0건.

## 🎯 T-2. 정확성 · UX

- [ ] **T-203** 캐싱 전략 — 홈·`/news/[id]`에는 `force-static` + 5분 ISR이 적용돼 있다. **supabase-js fetch가 캐시 옵션 없이 나가므로 `revalidate`만으로는 동적 상태에 남아 있어 `force-static`이 필수다.** 잔여: `/news`·`/posts`는 `searchParams`, `/posts/[id]`는 세션에 의존해 동적이다. 필터를 경로 세그먼트로 옮기거나 관리자 UI를 클라이언트 세션으로 바꾸면 ISR을 확대할 수 있다. `revalidateTag` 세분화도 시작하지 않았다.
